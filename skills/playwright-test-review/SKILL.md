# Playwright test review

Review the tests the user points to. Report findings; do not rewrite the file unless asked.

For each test, ask the question that matters most: **what change in the product would make this test fail?** If the answer is "almost nothing", the test is weak however green it is.

## Checklist

### Waiting and timing

- `waitForTimeout` or any fixed sleep. Replace with a web first assertion on what the user would see.
- A value read with `textContent`, `innerText`, `count` or `all` right after an action that changes the page. These do not wait. The read can happen before the new view renders. Wait for an element that only exists in the new state first.
- `toHaveURL` used as proof that a page loaded. In a single page app the URL can change before the view does.
- `networkidle` as a general wait.
- `isVisible()` inside an `if` or a plain `expect(await ...isVisible()).toBe(true)`. Neither retries. Use `await expect(locator).toBeVisible()`.

### Locators

- CSS chains, XPath, `nth` or text that depends on layout. Prefer role, label and test id.
- A locator that can match more than one element. Strict mode will fail later, on another browser or another dataset.
- Selectors repeated across tests instead of living in one page object.

### Assertions

- A test with no assertion, or only an assertion that the page did not crash.
- Asserting on what the test itself typed instead of what the product produced.
- A hardcoded expected value that the test could compute and verify from the page, such as a total.
- `toBeTruthy` on a locator. A locator object is always truthy.
- Negative checks that pass when the page has not loaded yet, for example `toBeHidden` on an element that has not had time to appear.

### Isolation and data

- Tests that depend on the order they run in, or on data left by another test.
- Shared accounts or records changed by parallel tests.
- Data created and never cleaned up.
- Login through the user interface in every test, where a saved session would do.

### Structure

- Assertions inside page objects.
- One test checking several unrelated things.
- A test name that describes the steps instead of the behaviour.
- `test.only`, `test.skip` without a reason, or commented out assertions.

## Report format

Group findings by severity:

1. **Will cause flaky failures**
2. **Can pass when the product is broken**
3. **Maintainability**

For each finding give the file and line, what is wrong, why it matters in one sentence, and the corrected code. If a category has no findings, say so. End with one line on whether the file is ready to commit.

## Verifying a fix

A change made for flakiness is not proven by one green run. Ask the user to run the test repeatedly on every configured browser, for example:

```
npx playwright test path/to/file.spec.ts --repeat-each=10
```
